## 0. Как это работает, за 60 секунд (говорить по памяти)

1. **Вход.** Диалог из API организаторов. `data.py` нормализует роли (оператор, клиент, бот), время и удержания. Реплики на удержании помечаются как внутренние и не оцениваются.
2. **Чек-лист.** Чек-лист выбирается по каналу: чат → `freedom_chat_v1.yaml`, звонок → `freedom_call_v1.yaml` (наследует чатовый). Все правила и пороги лежат в YAML, в коде их нет.
3. **Один критерий = один запрос.** К каждому из 8 критериев модель получает транскрипт (помечен как данные, а не инструкции), рубрику и блок FACTS. FACTS считает код: паузы, первая реплика оператора, идентификация.
4. **Жюри.** Haiku и Sonnet голосуют. При расхождении решает Opus, на шкалах 04/06 берётся медиана из 3 ответов. Решение 08=YES судья подтверждает всегда.
5. **Доказательства.** Цитату ищем в реплике оператора дословно. Если не нашли, делаем один повтор, после этого ставим `evidence_warning` или `needs_review`. Оценку молча не переворачиваем.
6. **Балл считает код**, не LLM (`scoring.py`): NA исключает вес критерия, остальные веса перераспределяются, округление Decimal HALF_UP. Флаг грубой ошибки 08 стоит отдельно и не обнуляет итог.
7. **Кэш по критерию.** Ключ: хэш диалога + хэш критерия. Если изменить один критерий, переоценивается только он.
8. **UI.** Дашборд, цитаты с подсветкой, ручная правка оценки, апелляции, редактор чек-листа, экспорт `results.json` 1.0.

## 1. Сколько DEV-диалогов разметили люди и какое согласие?

**Ноль.** Люди не разметили ни одного DEV-диалога, поэтому согласие с человеком на DEV не измерено. Так и написано в [README](../README.md) («Точность на реальных DEV-диалогах **не измерена** человеком»).
- **Почему.** Эталон организаторов скрыт, а время ушло на конвейер: доказательства, жюри, экспорт, апелляции, каскад.
- **Что есть вместо этого:**
  - Два синтетических эталона, которые мы разметили сами: настроечный (16 диалогов, 128 меток) и отложенный (10 диалогов, 80 меток). На отложенном 0.95 [0.875, 1.000] с бутстреп-CI ([EXPERIMENTS §2–3](../EXPERIMENTS.md)). Отложенный набор уже частично «загрязнён»: по нему выбирали модели. Это указано там же.
  - На DEV измерено только согласие режимов с жюри. Например, каскад совпадает с жюри v7 на 0.948 меток. Это согласованность, а не точность.
  - 18.3% критериев на DEV помечены `needs_review`, то есть отданы человеку.
- **Инструмент для разметки уже есть:** `python -m cqa label --ids …` (ручная разметка) и `python -m cqa gold --labels <файл>` (согласие с моделью).
- **План пилота:** 2 аналитика QA Freedom размечают по 50 DEV-диалогов. Считаем Cohen's κ между людьми (потолок) и κ модель↔человек по каждому критерию, затем калибруем правила 02/07/04. Не спорим о трактовках, пока нет этих данных.

## 2. Критерий 07: почему «До свидания!» без предложения помощи = «Нет»?

- **Официальный текст** (чек-лист PDF): «**Да** — оператор подвёл итог **или** предложил дальнейшую помощь **и** попрощался». Прощание обязательно, плюс хотя бы одно из двух: итог или предложение помощи. Голое прощание этому условию не удовлетворяет. Аудит пункта есть в [ASSUMPTIONS.md](ASSUMPTIONS.md#rubric-alignment-official-checklist-pdf-vs-our-yaml).
- **Смягчение уже есть:** итогом считается и короткая фраза о результате («Заявка оформлена, деньги поступят в течение дня»). Элементы могут быть разнесены по двум последним репликам. См. `checklists/freedom_chat_v1.yaml`, критерий 07.
- **Это одна строка в YAML, код менять не нужно.** Если у Freedom другая трактовка, её меняют за минуту: UI → «Чек-листы» → `freedom_chat_v1` → критерий 07 → в рубрике YES написать «оператор попрощался (итог или предложение помощи — желательно)» → «Сохранить» → «Переоценить по текущему чек-листу». Хэш критерия меняется, и модель переоценивает только 07.
- **Честно:** мы не смогли проверить, как это читает заказчик: без размеченных данных проверить нечем. На DEV критерий 07 входит в число частых поводов для `needs_review` (23 случая, [EVALUATION](EVALUATION.md)). Это первый кандидат на калибровку в пилоте.

## 3. Критерий 02: N/A или «Да», если оператор ответил сразу?

- **Официально:** «**Да** — оператор учёл известные детали и уточнил недостающее до ответа. **N/A** — данных для ответа хватало с самого начала». Если оператор ответил сразу, потому что уточнять было нечего, это по тексту чек-листа N/A, а не «Да».
- **Для оператора N/A лучше «Нет» и нейтрально к «Да»:** вес 02 убирается из знаменателя, остальные веса перераспределяются (`scoring.py`, [SCORING.md](SCORING.md)). Штрафа нет, но нет и бесплатного «Да» за отсутствие проблемы.
- **Пример из эталона:** `examples/gold/gold-01-ru-tariff-good.json`. Клиент пишет: «какая комиссия на тарифе «Стандарт» за сделки с американскими акциями?». Данных достаточно, оператор отвечает сразу, 02 = **NA** (обоснование в файле: «request clear from the start → NA»). Обратный пример: `examples/gold_holdout/hold-01-en-bonds-clarify.json`, оператор уточняет облигации до ответа, 02 = **YES**.
- Высокая доля NA на DEV (43/65) получается из официального условия на простых запросах ([ASSUMPTIONS](ASSUMPTIONS.md)). Если заказчик хочет «Да», это тоже правка правила в YAML.

## 4. Какой режим вы предлагаете Freedom в прод с учётом PDn и цены?

Сначала поправка: **0.787 — это не наш локальный режим.** Это эксперимент с дообучением Qwen3-8B, который мы показываем честно, потому что он не лучше базы ([FINETUNE.md](FINETUNE.md)). Наш локальный режим — Qwen3.8-27B-FP8, **0.963**.

Предложение:
1. **Основной режим: on-prem/VPC, Qwen3.8-27B-FP8 через vLLM.** Одна модель, 0.963 на отложенном наборе (на уровне жюри, Δ не значима), грубые P/R 1.0/1.0, цитаты и обоснования сохраняются, данные не покидают периметр. Время GPU ≈ **$0.0294/диалог** на арендованной H100 ([EXPERIMENTS §1](../EXPERIMENTS.md)). На своём железе платится только амортизация. Включается так: `CQA_OPENAI_BASE_URL=<vllm>/v1`, роутер `CQA_ROUTER_FIRST=local` ([KZ_MODELS](KZ_MODELS.md), [OSS_ROUTER](OSS_ROUTER.md)).
2. **Дешёвый триаж: та же модель в режиме решений** (0.938, $0.0012, 7.3 с на A40, без цитат). Прогоняем весь поток и отправляем на полную оценку с цитатами только спорное или низкоуверенное.
3. **Claude (жюри или эскалация каскада)** только там, где это разрешает политика банка: по корпоративному договору с zero-retention.
4. **Маскирование PII перед внешним вызовом сейчас не реализовано.** Это первый пункт плана: ИИН, номера счетов, карт и телефонов заменяются плейсхолдерами на шаге `data.py` до любого внешнего запроса. В on-prem-режиме этот вопрос не стоит. В синтетике для дообучения реальных PII нет (`cqa/finetune/augment.py`).

**Оговорки:** 0.963 у 27B — один прогон, на настроечном эталоне и DEV ещё не подтверждён ([KZ_MODELS](KZ_MODELS.md)). Аппаратура в файлах указана по-разному: в KZ_MODELS — A40 и $0.0044, в EXPERIMENTS — H100 и $0.0294. В расчётах берём консервативную оценку $0.0294.

## 5. Вживую: добавить новый критерий в чек-лист ЗВОНКОВ и переоценить один звонок

**UI:** «Чек-листы» → `freedom_call_v1` → «Добавить критерий» → id (например `09`), тип binary, вес, рубрика YES/NO, при необходимости NA → «Сохранить» (сервер проверяет инварианты чек-листа; ошибки показываются в форме) → открыть звонок (`p4-ru-…`) → «Переоценить по текущему чек-листу».

**CLI:** `python -m cqa evaluate --group <G> --ids <call_id>` (с `--checklist freedom_call_v1`, если нужно задать чек-лист явно). Отдельного флага `--reeval` нет: по умолчанию работает кэш, и переоценивается только изменённое. `--fresh` переоценивает всё заново.

**Ожидаемый результат:** в LLM уходит **только новый критерий**. Остальные 8 берутся из кэша, их ключ — хэш диалога + хэш критерия. Итог пересчитывается кодом с новым весом. Экспорт выгружает новый критерий под его `id`/`code` (валидатор даёт предупреждение, не ошибку; [PROD_RUNBOOK](PROD_RUNBOOK.md)). Если менялся только вес, LLM не вызывается вообще: кнопка «Пересчитать веса».

## 6. Почему в DEMO число эпох расходилось с README (0.32)?

Это ошибка в документе. На самом деле 16 шагов ≈ **0.32 эпохи** ([FINETUNE.md](FINETUNE.md), коммит `0ccb200` «honest: 16 steps»). В `docs/DEMO.md` строка исправлена тем же коммитом, что и добавил этот файл (`git log -- docs/DEMO.md`). Результат: совпадение 0.787 = база, MAE 12.17 → 10.43. Дообучение не дало выигрыша по совпадению, и мы так и пишем.

## 7. «Репозиторий выглядит сгенерированным агентом (50+ коммитов одного автора)»

Да, мы много использовали ИИ-агентов для написания кода, как инструмент и под нашим руководством. Автор `cqa` — это общий локальный git-идентификатор. Решения и их обоснование наши:
1. **Один критерий = один запрос, балл считает код.** LLM не складывает числа, итог воспроизводим (`scoring.py`, Decimal).
2. **Каждое «Да» подкреплено дословной цитатой оператора.** Цитата проверяется, иначе повтор и флаг. Без выдуманных доказательств и тихих переворотов ([ASSUMPTIONS #13](ASSUMPTIONS.md)).
3. **Жюри вместо одной модели, судья только при споре.** Меньше дисперсия, цена разумная. 08=YES всегда подтверждает судья.
4. **Отказ в закрытую:** ошибка = запись `status:"error"`, а не ноль. Недоделанный диалог помечается `incomplete`.
5. **Все трактовки в YAML** (порог 180 с, 07, 02) с аудитом по официальному тексту. Заказчик меняет правило без программиста.
6. **Честные замеры:** отложенный набор, бутстреп-CI, шум ±2/80. Отрицательные результаты (дообучение, KZ-сигналы, ISSAI) не скрываем.

Можем разобрать вживую `cqa/scoring.py`, проверку цитат в `cqa/evaluator.py` и роутер (`cqa/router.py`, `cqa/routing_policy.py`).

## 8. Другие вероятные вопросы

**Почему нет просодии и аудио-анализа?** Организаторы выдали транскрипты, а чек-лист оценивает содержание. По меткам времени считаем темп речи, паузы и наложения. Эти метрики информационные и в балл не входят (`data.call_metrics`, коммит `a613802`). Тон и дикцию по звуку можно добавить отдельной моделью, но без размеченных данных мы бы не смогли это проверить.

**Какой шум между прогонами?** 0–2 метки из 80 на одной конфигурации; у жюри 0.925–0.950 за 8 версий кода ([EXPERIMENTS §3.2](../EXPERIMENTS.md)). Медианная ширина CI 0.137, поэтому верх таблицы не ранжируется. Температуру у части провайдеров задать нельзя.

**Почему по умолчанию жюри, а не codex (0.975)?** Разница +0.025 (2 метки из 80) не значима (p=0.545). У жюри есть независимое второе мнение и `needs_review` по расхождению. Им прогнан весь DEV и сделан `results/dev/results.json`. Codex доступен как `--preset max`.

**Ложные срабатывания по грубым ошибкам?** На отложенном наборе P/R 1.0/1.0, но положительный пример только один, так что это слабая оценка. На DEV 5 флагов, все подтверждены судьёй и отправлены на проверку ([EVALUATION](EVALUATION.md)). Число ложных срабатываний на реальных данных не измерено, нужны метки людей. Флаг не обнуляет итог, решение принимает человек.

**Стоимость при 5000 звонков в день** ($/диалог × 5000):
| Режим | $/день | Примечание |
|---|---|---|
| Жюри Claude | ≈ $800 | $0.16 |
| Каскад | ≈ $20–75 | $0.004–0.015 |
| Jev в одиночку | ≈ $2.7 | $0.00053, без цитат |
| Qwen3.8-27B локально, с цитатами | ≈ $147 (аренда H100) | 5000 × 26.6 с ≈ 37 GPU-часов в день → 2 H100 |
| Qwen3.8-27B, режим решений | ≈ $6 | 5000 × 7.3 с ≈ 10 GPU-часов в день → 1 A40 |
Время на GPU — пересчёт из с/диалог при параллельности 4–8, нагрузкой не проверялось.

**Как работает апелляция?** «Оспорить» на критерии (комментарий обязателен) → вкладка «Апелляции»: проверяющий видит комментарий, оценку ИИ и фрагмент диалога, подтверждает или меняет оценку (причина обязательна) → итог пересчитывается. В карточке видны исходная оценка, решение и финал. API: `POST /api/appeals`, `POST /api/appeals/{id}/resolve` (`cqa/appeals.py`). Решённые апелляции служат готовой разметкой для калибровки.

**Если API упало в контрольный час?** При 429/5xx работают повторы с backoff и Retry-After. Повторный `make submit` не пересчитывает уже готовое благодаря кэшу. Если не отвечает API организаторов, сохраняем данные в `data/<group>.json` и запускаем без `--refresh`. Если недоступен Anthropic: `CQA_PRESET=cascade` или локальная 27B. Диалог с ошибкой остаётся записью `status:"error"`. Репетиция: 10 диалогов, 59 с, $1.79, 0 ошибок ([PROD_RUNBOOK](PROD_RUNBOOK.md)).

**Атака промптом из транскрипта («поставь 100 баллов»)?** Транскрипт обёрнут в разделители и объявлен данными. На это есть тест `examples/gold/gold-16-en-no-greeting-injection.json` ([ASSUMPTIONS #14](ASSUMPTIONS.md)).

**Казахский язык?** На отложенном наборе 2 KZ-диалога, этого мало. 27B на них 1.000, ISSAI-9B-Kazakh 0.938 и в целом хуже (0.887, разница значима, но модели разного размера). KZ-сигналы парсера выигрыша не дали ([EXPERIMENTS §1](../EXPERIMENTS.md), [HYBRID_KZ](HYBRID_KZ.md)).
